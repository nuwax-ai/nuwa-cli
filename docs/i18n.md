# UI language (i18n)

`nuwa-cli` ships with a lightweight built-in i18n layer. The default UI language is **English**; **Simplified Chinese** (`zh-CN`) is shown automatically when the system locale is Simplified Chinese. There is no new runtime dependency — the message bundles and the `t()` resolver live in [`src/util/i18n/`](../src/util/i18n).

## Resolution order

The active language is resolved, in priority order:

1. **`NUWACLI_LANG` env var** — highest priority; a one-off override for the current process.
2. **`lang` field in `~/.nuwa-cli/config.json`** — persisted by `nuwa-cli lang`; survives restarts.
3. **Auto-detection** from POSIX locale env vars (`LC_ALL` → `LC_MESSAGES` → `LANG` → `LANGUAGE`). A value identifying Simplified Chinese (`zh`, `zh-CN`, `zh_Hans`, `zh_CN.UTF-8`, …) selects `zh-CN`.
4. **`en`** — fallback default.

`auto` (set via `nuwa-cli lang auto` or `NUWACLI_LANG=auto`) clears the explicit choice and re-runs detection.

### Simplified vs Traditional Chinese

Only **Simplified** Chinese locales map to the `zh-CN` bundle. **Traditional** Chinese locales (`zh-TW`, `zh-HK`, `zh-MO`, `zh-Hant`) have no bundle and fall back to **English** — they are not silently mapped to Simplified.

## Switching the language

```bash
nuwa-cli lang               # show the current language and how it was resolved
nuwa-cli lang zh-CN         # persist Simplified Chinese to ~/.nuwa-cli/config.json
nuwa-cli lang en            # persist English
nuwa-cli lang auto          # follow the system locale again

NUWACLI_LANG=zh-CN nuwa-cli doctor   # one-off override (highest priority)
```

`nuwa-cli lang` with no argument prints the active language and which source it came from (`env` / `config` / `detect` / `default`).

The first-time install wizard (`npx @nuwax-ai/nuwa-cli@latest install`) can also persist `lang` via an interactive select or `--lang en|zh-CN`, writing the same `~/.nuwa-cli/config.json` field as `nuwa-cli lang`.

## What gets localized — and what does not

| Surface | Localized? |
|---|---|
| Terminal output (`console.log/error`, spinner text, `--help` descriptions, prompts, status lines, thrown user errors) | ✅ Yes |
| **ACP protocol responses** (HTTP `error.message`, SSE event payloads, permission `outcome`/`optionId`/`reason`, the `{ok,error:{code,message}}` envelope) | ❌ **Always English** |

ACP responses are consumed by clients and engines (NuwaClaw, cloud routing, the ACP SDK), not by humans reading a terminal. They are kept in English on purpose, aligned with NuwaClaw and the shared `@nuwax-ai/agent-kit` library (which explicitly keeps protocol-layer messages English and outside i18n). Only the human-facing terminal output honors the language setting.

## Implementation notes

- Bundles: `src/util/i18n/en.ts` is the **baseline** (`as const`, the source of truth for the key set); `src/util/i18n/zh-CN.ts` is typed as `{ [K in keyof typeof en]: string }`, so a missing Chinese key is a **compile-time error** (stronger than a runtime consistency check).
- `t(key, vars?)` does `{name}` placeholder substitution only. There is no ICU/MessageFormat/pluralization — the project's strings don't need it.
- The first `t()` call resolves the language (env → config → detect → default) and caches it. Commander help text is registered synchronously, so the locale is already resolved by the time `.description(t(...))` runs.
- Adding a string: add the key to **both** `en.ts` and `zh-CN.ts`, then use `t("namespace.key", { ... })` at the call site. Keep ACP-facing strings as plain English literals — do **not** route them through `t()`.
